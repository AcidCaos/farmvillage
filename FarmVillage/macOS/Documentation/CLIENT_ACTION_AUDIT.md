## Summary

1. **Farming goes through one AMF method.** Every world action is `WorldService.performAction`, built by `Transactions:TWorldState.signedWorldAction`. The client sends roughly 70 distinct action-name literals through it (approximate count from the call-site list). About 35 are relevant to farming. Client-side senders are listed in the table below.
2. **The server persists only a few of them.** `commands.world_perform_action` (commands.py:339) has explicit write branches for `plow`, `place`, `harvest`, `move`, `clear`/`clearWithered`, `sell`, `store`, and `use` (consumption only). `instantGrow` has its own module. `neighborAct` writes the host farm. `getStorageInfo` and `TransformBuilding` are read or breeding paths.
3. **Any other performAction name is a silent acknowledgment.** It falls through the if/elif chain with no write. It then returns a success envelope with `id` and `data`. Nothing reaches `LocalData/unhandled.log`, because that log only records top-level gateway names (server.py:975-977).
4. **Unknown top-level gateway names return `data: null` with `errorType 0`.** They are logged to `unhandled.log`. Several farming-adjacent services are in this state (Section 2).
5. **Rejections are HTTP 400 for the whole batch.** Any `ValueError` raised during a gateway request returns 400 "Invalid game command parameters." The farm is rolled back (server.py:485-503; player.py:411 `village_transaction`). The client retries, then faults. The `TransactionManager` dispatches a `TransactionFaultEvent` (`HTTP <code>`) on this path.
6. **Ordinary farming, silent loss (resolved 2026-10-23 for the performAction names).** Before this change these client actions succeeded on screen but changed nothing on the server: `HarvestReadyNow`, `CompleteNow` on non-construction items, `redeemNeighborFertilize`, `redeemNeighborUnwither`, `makeSlop`, `ExpandWithCurrency`, `upgradeBuilding`, `upgradeStorage` / `purchaseStorageUpgrade` / `cancelStorageUpgrade`, `transform` on ordinary animals, `deprecate`, `paint`, `wither`, the cosmetic and reward names in row 27-29, and the per-plot effect of irrigation (not a performAction name, still open). Now `RemoveAltGraphic` and `setFeaturedItem` persist (validated), and every other listed name raises HTTP 400 with no save change (rows 12-29). A rejection rolls back the whole HTTP batch, so an unrelated call sent in the same batch fails with it.
7. **Ordinary farming, hard rejection.** `CompleteNow`, `HarvestReadyNow`, `ExpandWithCurrency`, and `upgradeBuilding` on construction-managed buildings (turkeyroost, orchard, horse stable) are rejected by commands.py:471. Breeding animals reject most actions via breeding.py:1040. Season advance (`WorldManager.loadNextSeason`) sends `shouldFreeze=true` and `nextSeasonUnlock=true`, and `world_travel.switch` rejects those flags. The `swapFarm` path that `PostInitSettings` can also reach was not fully traced (uncertain).
8. **Lighthouse Cove is strictly fenced.** creative_worlds.py:442-451 allows only `plow`, `place`, `move`, `harvest`, `clear`, `sell`, `store`, and `getStorageInfo`. `instantGrow` and `neighborAct` bypass the fence. Cove also rejects any action on a plot flagged `isJumbo`, `isBigPlot`, `isProduceItem`, or `isSuperPlot` (creative_worlds.py:447), including clear, sell, harvest, and move. A fertilized plot in Cove can become stuck (uncertain: depends on whether Cove visitors can fertilize; see Section 6).
9. **Equipment is the best-covered non-performAction path.** `EquipmentWorldService.onUseEquipment` (server.py:680, `commands.equipment_use`) handles `plow`, `place`, `harvest`, `plotRemove`, and `combine`. The resource harvester and per-plot irrigation are not handled.
10. **Peaceful mode turns off withering by default.** `peaceful.enabled()` is True when no `peacefulMode` key exists (peaceful.py:14-16). `clearWithered`, the wither toggle, and unwither paths are therefore dormant by default. The wither toggle still reports success without doing anything.

Parameter shape: observed AMF arrives as a dict keyed by integers, not a list (`{0: {...}, 1: {'firstWA': True}}`, from `LocalData/Logs/wrapper.log`). Handlers that iterate `params` see integer keys. `world_travel.guard_world_context` (world_travel.py:175-180) therefore checks only the snapshot, not the params. `instant_growth._options` already handles the dict shape.

Trace evidence: 33 live `WorldService.performAction` calls in `LocalData/Logs/wrapper.log`: `getStorageInfo` 15, `harvest` 8, `place` 6, `plow` 4. The log also shows 77 gateway 409 responses from the God Barn guard (`LocalData/runtime/GodBarn/integration.py`, parked-farm check). These are a test-environment confound, not an action gap. `LocalData/runtime/` is an older snapshot without the `instantGrow`, `getStorageInfo`, and `TransformBuilding` branches. It was not audited.

## Classification key

- **IMPLEMENTED**: explicit server branch writes state.
- **IMPLEMENTED (early)**: handled by a module before the generic branch.
- **PARTIAL**: branch runs but does not persist everything the client implies.
- **REJECTED**: explicit `ValueError` (HTTP 400). Listed with the rule that triggers it.
- **SILENT**: no branch matches. Success envelope, no state change.
- **MISSING**: gateway name not in server dispatch. Returns `data: null`, `errorType 0`, logged to `unhandled.log`.

## 4. Verified as not a problem

- performAction params are an array of the client's arguments (rest arguments), which the trace confirms (`{0: {...}}` shape). When the first world action of a Flash session is not `move`, the client appends `{firstWA: true}`. The earlier concern that the client calls `push` on a plain Object does not apply, because the arguments are an array. The server tolerates the marker in `pets.py:55` and `breeding.py:956`. `instant_growth._options` does not (see row 10).
- `Plot.executeNeighborPlow` (used by `PlowNeighborAction.redeem`) sends `plow` against the redeemer's own farm. That is the intended target, so it is not a cross-farm write.
- `TTransformBuilding.perform` sends no params, so `breeding.transform_baby` does not hit the dict-iteration issue at breeding.py:956.
- `TWitherOn` uses `UserService.toggleWither` via `signedCall`, not `performAction`.

## 5. Lighthouse Cove fence (creative_worlds.py:442-512)

Allowed by name: `plow`, `place`, `move`, `harvest`, `clear`, `sell`, `store`, `getStorageInfo`.

Rejected by name (400), with messages:
- `use` (consumables), `clearWithered`, `CompleteNow`, `HarvestReadyNow`, `redeemNeighborFertilize`, `redeemNeighborUnwither`, `makeSlop`, `wither`, `upgradeBuilding`, `ExpandWithCurrency`, `paint`, `deprecate`, `transform`, `TransformBuilding`, all storage-upgrade names, and all alternate-graphic and overlay names.

Rejected by flag (400): any action whose snapshot has `isJumbo`, `isBigPlot`, `isProduceItem`, or `isSuperPlot` (creative_worlds.py:447, "Specialized Lighthouse Cove plots are not restored."). This runs before the allow-list check, so it blocks clear, sell, harvest, and move too.

Bypasses the fence: `instantGrow` (own module), `neighborAct` (commands.py:346).

Host-side write risk: `neighbor_act` persists the host's object without applying the host's own Cove rules. If a visitor's `fert` sets `isJumbo` on a Cove host's plot, the host's next action on that plot is rejected. **Uncertain**: needs `isFertilizable` and Cove behavior traced.
